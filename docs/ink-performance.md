# ink 性能写法

> RPG PRD §4.5 / R2 的产物(2026-11-10)。一局长的游戏(地城爬行、几百个选择)在 ink 里会跑上百万步,写法差一点,手机上就卡,`check-ink --random` 就慢。这篇讲怎么量、哪些写法贵、引擎替你做了什么。

## 先量,再改

- **耗时**:`npm run check-ink -- <文件夹> --random 300`。机器忙的时候墙钟时间能差三成,比较两个版本要交替各跑几次、取最小值。
- **步数**:inkjs 每执行一条指令算一步(`Story.Step`)。步数不受机器负载影响,是最稳的指标。在 `Story.prototype.Step` 上挂一个计数器,同时记下当前容器路径的第一段(函数或段落名),就知道步数花在哪个函数里。
- **行为不变**:优化前后用**固定种子**跑同一批对局(4AD 的机器人 `--seed 7 --stats`),输出要逐字一致。不一致就是改错了,哪怕看起来只是"更快"。

## 贵的写法

1. **函数调用本身就贵。** 调一次 ink 函数(进出栈、传参、返回)要十几到二十步,比函数体还贵。热点里的小函数(取一个值、比一下)在调用处直接写成表达式。
2. **按序号取值的 switch 很贵。** `{ i: - 1: ~ return life_m1 - 2: … }` 每次约 35 步;同样的事交给引擎(`member_get(i, "life")`)约 10 步。
3. **`&&`、`||` 不短路。** 两边都会算。贵的判断别放在 `&&` 后面指望它被跳过;先用 `{ 便宜的条件: … }` 挡一层。
4. **选项文字不管条件成不成立都会求值。** `+ {can_cast(i)} [{who_name(i)}施法]`:哪怕条件是假,`who_name(i)` 也会算。一个回合几十个选项、每个选项几次函数调用,就是几千步。选项文字里只放便宜的东西。
5. **派生出来的文字存起来。** 名字、称号这类"由别的变量算出来、很少变"的东西,放进变量,在源头变的地方(设职业、换装备)重算一次,读的时候直接读变量。4AD 的队员名字这样改了以后,机器人快了三成。
6. **能用 temp 就用 temp。** 同一个值在一段里要用好几次,先 `~ temp x = …` 存下来。

## 引擎替你做的

- **查表**:`table_text`、`table_id` 由引擎直接查(生成的 ink 版本是把所有表的所有行挨个比一遍,留作不开引擎时的后备)。两边按同一个顺序(`lookupOrder`)找行、同样转义文字,结果逐字一致。
- **队员**:`member_get(谁, "变量")` 读 `<变量>_<队员 id>`(谁 = 从 1 开始的序号或 id;任何按队员声明的变量都行,不限于小队属性);`party_count("变量", 值)` 数有几个队员的这个变量等于这个值。不存在的队员给这个变量类型的"零"(列表是空列表、布尔是 false、文字是空串),所以 `member_get(i, "gear") ? 刀` 不用先判断 i。
- **会话**:重新开始、回退、读档时,剧本 JSON 只解析一次(inkjs 自带的 JSON 读取很慢)。
- **inkjs 的一个热点**:inkjs 每走一步都要问一次"是不是在拼字符串",它的写法每次对输出流的每一项调一个类型检查函数。Inkwright 换了一个等价的写法(`src/play/inkjs-speed.ts`,有逐步对照原写法的测试)。

试过但没做的:重新开始时复用同一个 Story(`ResetState`)。inkjs 的 `ResetState` 不清 Story 上记着的"上一步在哪些容器里",新一局开头的访问计数会算错,4AD 的结果就变了。

## 4AD 上的数字(2026-11-10)

| | 之前 | 之后 |
|---|---|---|
| 每个选择的 ink 步数 | 8490 | 4110 |
| `check-ink --random 300`(同一台机器交替跑,取最小) | 48.4 秒 | 23.1 秒 |
| 机器人 100 局(固定种子,输出逐字一致) | 87 秒 | 约 55 秒 |

改了什么:引擎侧的查表和 `member_get`/`party_count`、会话只解析一次 JSON、inkjs 热点;4AD 那边把按序号取值的二十多个 switch 换成 `member_get`、在调用处展开小函数、名字存进变量。
