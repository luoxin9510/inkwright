# Inkwright 通用 RPG 引擎 PRD

> 状态:进行中。R1 已做(2026-11-10):动态实体(配置、存储、生成的 ink、引擎函数)、面板上的敌人区和网页里的列表、表格的行刷出实体(`spawn_from`)、小队成员走同一套函数(`"party"` 种类)、随机对局按种类统计。剩下:原创小地城示例和 4AD 改写。固定实体就用 `party:` 写,不另加 `entities:`:两种写法做同一件事只会让作者犹豫。
>
> 起草:2026-11-10。这份 PRD 改变了方向:`game-engine-prd.md` 和 `tabletop-prd.md` 的非目标"不做通用 RPG 框架"从这里起作废,改成本文的做法。两份旧 PRD 里已经做好的部分照样有效,本文在它们上面接着做。

## 1. 背景与目标

Inkwright 现在是"ink 写剧本 + `game.md` 声明规则 + 引擎显示和检查"。检定、资源、物品、随机表、牌堆、手牌、地图、生长的地城、小队、记录、回合、神谕都已经有了,工具也成套:`check-ink` 穷举和随机对局、存档重放、实时日志、导出网页。**通用的是"规则怎么显示、怎么测",不通用的是"规则本身"**:每个游戏的战斗、队伍、成长都要自己用 ink 从头写。

4AD 移植是证据。手写约 6,900 行 ink、325 个函数、328 个变量,其中队伍、战斗、怪物、宝藏约 4,000 行,几乎任何地城游戏都要再写一遍。ink 跑重逻辑很慢(函数调用贵、`&&` 不短路),CI 一度要 30 分钟;队员属性只能拆成 `life_m1` 这样的扁平变量,写起来绕。

**目标**:让作者用 Inkwright 做出四类 RPG,规则写一次、很多游戏共用:

| 类型 | 例子 | 核心 |
|---|---|---|
| 叙事型 | 宿舍怪谈、Disco Elysium 式 | 检定、心声、资源、关系 |
| 地城爬行 | 4AD 式 | 队伍、怪物、战斗、宝藏、生长的地图 |
| 单人跑团 | 日志游戏、Ironsworn 式 | 神谕、提示表、时钟、记录、日志 |
| 回合战斗 | JRPG 式 | 敌我双方、行动顺序、技能、状态 |

**用户**:先给作者本人用(会写 ink,也会改代码),但从第一天起按"别人也能用"来做:格式稳定、报错说人话、每样东西有教程和模板。之后的用户是会写 ink、不写代码的作者,他们用现成的**规则系统包**,只写剧情。

**定下的约束**(作者 2026-11-10):

1. 四类都要做,但一次推进一类,每一刀都由一个真实的游戏验收。
2. 剧本继续以 ink 为主。
3. 导出网页和手机上玩必须一直能用,所以规则不能是用户写的 JS。

## 2. 原则

- **状态只在 ink 里。** 重放、存档、穷举、换设备都靠它。引擎可以替 ink 算,但结果写回 ink 变量。
- **引擎函数必须可重放。** 引擎绑定的函数要么是纯函数(同输入同输出,lookahead 反复调用也没事,像现在的记录和地城),要么走这一局的种子骰子。
- **规则是数据加 ink,不是脚本。** 新能力都按同一套做:
  1. `game.md` 里声明;
  2. 生成 ink,并带上没有引擎时的回退(Inky 里预览可以降级,但不能编译失败);
  3. 面板和网页都显示;
  4. `check-ink` 和随机对局认识它;
  5. 写一节教程。
- **加原语,不加框架。** 引擎提供"实体、背包、状态、成长、引擎侧计算"这些积木;某一套战斗怎么打,写在系统包的 ink 里,不写进引擎。
- **不破坏已有的游戏。** 旧的 `game.md` 照样能用。新格式靠 `schema` 区分,必要时由引擎迁移;`party` 继续保留,作为实体的一种简写。
- **公开内容原创。** 私有规则书(4AD 等)只在私人仓库里用这些原语改写,不进公开仓库、系统包和教程。

## 4. 新原语

### 4.1 实体

**一组有属性的东西**:队员、怪物、NPC、召唤物。是这份 PRD 的地基。

```yaml
kinds:
  - id: hero
    name: { zh: 英雄, en: Hero }
    stats:
      - { id: life, name: { zh: 生命, en: Life }, max: life_max }
      - { id: life_max, hidden: true }
      - { id: level, name: { zh: 等级, en: Level } }
    down: life            # 0 及以下画成倒下
  - id: foe
    stats: [ { id: life, max: life_max }, { id: life_max, hidden: true }, { id: attack } ]
    remove: life          # 0 及以下从场上移走
entities:                 # 开局就有的(固定的)
  - { id: m1, kind: hero, name: 铁匠, stats: { life: 5, life_max: 5, level: 2 } }
```

- **固定实体**(开局就有、数量不变)照现在的小队生成扁平变量:读写快,穷举也认得。`party` 就是"一种 kind、固定成员"的简写,不改写法也能用。
- **动态实体**(打着打着冒出来、被消灭的):存在一个字符串变量里(和记录、地城同样的做法)。引擎绑定纯函数读写,生成的 ink 包一层好用的函数:

  ```ink
  ~ temp g = spawn("foe", "goblin")          // 返回新实体的 id
  ~ set_stat(g, "life", stat(g, "life") - 2)
  { alive("foe") == 0: -> victory }
  ~ temp t = pick("foe", "lowest:life")      // 选目标:最弱、随机、第一个
  ```

- **模板**:怪物从随机表或牌堆生成(`spawn_from("foe", table("monsters"))`),表格的一行带属性。牌已经有属性,这里把同样的写法用在表格的行上。
- **显示**:状态栏按种类分区。英雄是现在的队伍卡;敌人在正文和选项之间排成一排("敌人区",`tabletop-prd` 4.8 推迟的那一块)。
- **检查**:`check-ink` 对每个属性做越界检查;随机对局按种类统计(敌人平均活几回合、英雄怎么死的)。4AD 机器人的 `--why` 由这里取代,变成通用功能。
- **回退**:没有引擎时,动态实体的函数返回保守值(没有敌人)。Inky 里能编译、能走流程,但打不起来。文档里写明。

### 4.2 背包数量和装备栏

- 物品可以有数量:`inv_count("arrow")`、`give("arrow", 3)`、`take("arrow")`。只在物品标了 `stack: true` 时用数量,其他物品照旧用 LIST。
- 装备栏:`slots: [weapon, armor, ring]`,物品写 `slot: weapon`。只有装备着的物品,`modifiers` 才生效(现在是"带着就生效",老游戏不受影响)。
- 实体也能带物品和装备(现在小队已经有 gear)。
- 商店不做新原语:价格是物品的属性,买卖是 ink 的选项。教程里给一个写法。
- **R4 落地的做法(2026-11-10)**:`give`/`take`/`equip` 的参数是 LIST 的项(`give(arrow, 3)`),不是字符串,写错名字编译时就报错,和 `inv ? arrow` 一个写法。数量存在 `<物品>_n`,数量大于 0 时物品也在 `inv` 里;`take` 返回实际拿走几个;对不堆叠的物品,`give` 放进背包、`take` 拿走一个、`inv_count` 是 0 或 1。角色的起始数量写 `counts: { arrow: 12 }`。装备栏只做主角的(`VAR equipped`,`equip` 换下同一栏的另一件,开局每栏装上第一件带着的);小队成员的装备栏等有游戏要用再加。

### 4.3 状态效果

- `statuses:` 声明名字、`modifiers`、持续方式(几回合、直到休息、永久)。
- `add_status(who, "poison", 3)`、`has_status(who, "poison")`、`tick_statuses()`(回合结束时扣回合数)。
- 状态挂在实体或主角上,显示成卡片上的小标签。检定加值走现有的 `collectModifiers`。
- **R4 落地的做法**:所有人的状态存在一个字符串变量 `statuses` 里(`谁|状态|回合;…`),引擎绑定纯函数读写(和实体、记录一样);谁 = 实体或队员的 id,主角写 `"me"`(zh 预设 `"我"`)。回合数 ≤ 0 表示一直有效;再加一次取较长的。持续方式只分两种:按回合(`tick_statuses()` 由故事在它认为"过了一回合"时调用)和 `rest: true`(`rest_statuses()` 清掉)。"每回合扣血"这种效果写在规则的 ink 里,不进引擎。没有引擎时状态加不上(保守回退)。`check-ink --random` 统计每种状态上身几次、出现在多少局;可堆叠物品结束时的数量和资源一样给分布。

### 4.4 成长

- 经验是一个资源。`levels:` 写每级的门槛,`level_up_ready(who)` 告诉剧本该升级了。
- 升级给什么由剧本决定:加属性,或者从"天赋"里挑一个。天赋是一种物品(带 `modifiers`,`slot: perk`),所以不用新机制。
- 状态栏在可以升级时给一个提示。
- **R5 落地的做法(2026-11-10)**:`levels: { resource, at }`,`at[0]` 是 1 级;生成 `VAR level`、`next_level_at()`(到顶为 0)、`level_up_ready()`、`level_up()`(返回升没升)。只做主角的等级。天赋是不带 `slot` 的普通物品:装备栏一栏只放一件,天赋要能有好几个,所以不用 `slot: perk`。

### 4.5 引擎侧计算(性能)

- 热点循环交给引擎绑定的纯函数:对一组实体求和、找最大最小、过滤、排序、按条件挑目标。
- 这些函数只读状态、返回值,写回仍由 ink 的包装函数做,所以重放和穷举不受影响。
- 每加一个,都在 4AD 上量一次速度(`--random 300` 的耗时),写进验收。
- R2 已做(2026-11-10):引擎侧查表、`member_get`/`party_count`、会话只解析一次 JSON、inkjs 热点;4AD `--random 300` 从 48.4 秒到 23.1 秒(同机交替测),每个选择的步数从 8490 到 4110,固定种子的机器人输出逐字不变。见 `docs/ink-performance.md`。
- 附一篇"ink 性能写法"文档:`&&` 不短路;选项文字不管条件成不成立都会求值;函数调用贵;能用 temp 就用 temp。这些是 4AD 优化时得到的经验。

### 4.6 战役和角色延续

- 冒险结束时(剧本调用 `end_adventure()`,或者用一个命令),把主角或队伍写成一篇**角色卡笔记**,放在 `角色/` 文件夹:frontmatter 是属性、物品、经验、状态,正文是这一局的结语和日志链接。
- 下一个冒险的 `game.md` 写 `characters: { from: 角色/ }`,开局时选人就从这个文件夹里挑。读进来的角色卡是这一局 run 的一部分(存进 seeds 旁边),所以重放不会因为角色卡后来又变了而走样。
- 冒险之间的事(养伤、买东西、升级)可以是一个很短的"营地"剧本,也是普通的 ink。
- **R5 落地的做法**:写角色卡的时机是剧本里一行带 `#sheet`(点了选项后第一次出现时写,回退、读档、重放都不写;和 `#fx` 同一个规矩),或命令「保存角色卡」/`api.saveSheet()`;不做 `end_adventure()` 函数:ink 函数会被 lookahead 反复调用,写文件只能放在界面这一侧。文件夹是 `sheets:`(相对于游戏文件夹,默认 `角色`),文件名是角色名;再写一次时 frontmatter 整个换成新的,正文保留,加一段这次的结语(冒险名和时间做标题)。角色卡里多了 `level`、`resources`、`statuses` 三个字段,`characters` 手写时也能用。"读进来的角色卡存进 run"没有另做:角色卡变了要重新生成引擎,而玩到一半的局有 1b 的 build 保留旧版本,效果相同。只写主角,小队的角色卡以后再说。网页导出不写角色卡。

### 4.7 关系和 NPC

- NPC 是一种实体(`kind: npc`),属性里放态度、信任。
- 叙事型游戏里,"和某人的关系"显示在状态栏,剧本照常读写。这是 4.1 的一个用法,不另做原语。

## 5. 规则系统包

**一个文件夹,装着一套规则**。作者写一次,很多游戏共用;不写代码的作者直接拿来写剧情。

```
系统/地城爬行/
  system.md        # frontmatter:规则片段(kinds、skills、tables、statuses……)和 version
  rules.ink        # 战斗回合、搜房间、休息这些流程,用 4.1–4.5 的原语写
  表/              # 怪物、宝藏、事件表(笔记里的 markdown 表)
  模板/            # "新建游戏"用的起始剧本
  说明.md          # 怎么用,可以改什么
```

- 游戏的 `game.md` 写 `system: ../../系统/地城爬行`。引擎先读系统的配置,再叠上游戏自己的(同 id 的以游戏的为准)。生成的 `_engine.ink` 会 INCLUDE 系统的 `rules.ink`。
- **版本**:`system.md` 带 `version`。游戏可以写上自己要的版本;版本对不上时,面板和 `check-ink` 给出提示。
- **分发**:先是复制文件夹;之后在 ink-games 公开仓库放第一方的包,再做"安装系统包"命令(从网址下载到 vault,下载前要用户确认)。
- **R3 落地的做法(2026-11-10)**:第一方的包放在 inkwright 仓库的 `packs/<id>/`,随插件打包(`virtual:packs`)。"新建游戏"把包装进 vault 的 `规则包/<id>/`(已有的不覆盖,作者可能改过),把包的 `template/` 复制到新文件夹,并把 `system:` 改成从游戏到包的相对路径。`system:` 写成 `路径` 或 `{ path, version }`;版本只比主版本号,所以 `system.md` 的 `version` 要加引号(`"1.0"`,否则 YAML 读成数字 1)。`system.md` 的 `pack: { name, description }` 是给选择器看的,和 `version` 一样不进游戏配置。包里的 `表/` 等 `from:` 路径相对于包写,叠加时改成相对于游戏。`check-ink` 跳过含 `system.md` 的文件夹本身的 ink,包的 `template/` 照常检查,仓库里有测试保证模板的引擎是最新的、两种语言都能玩到结局。
- **第一方的包**(原创):
  - **叙事检定**:把宿舍游戏的检定、心声、恐惧整理出来;
  - **地城爬行**:原创规则,不抄 4AD;
  - **单人日志**:现在的日志型模板升级而来;
  - **回合战斗**:JRPG 式,敌我轮流行动、技能、状态。
  - **R6 落地的做法(2026-11-10)**:回合战斗包没有加任何引擎功能,全部是 R1–R4 的积木:队员是小队(`party`),敌人是实体种类 `foe`,行动顺序是 ink 里的递归函数——每回合把站着的人的 `acted` 清零,每次挑 `spd` 最高、还没动的(速度相同队员先),轮到队员就用线程(`<- attack_option(k)`)给出"攻击第 k 个敌人"之类的选项,轮到敌人就由规则自动行动;眩晕、防御、中毒都是 R4 的状态。伤害是攻击 + 2d6 − 4 − 防御(问题 6 定的 2d6)。穷举走不完一场战斗(状态太多),和地城包一样靠固定种子的测试和策略机器人量平衡。叙事检定包把《302》的规则、难度、技能和声音、恐惧和体力、同伴的恐惧和信任、恐惧修正搬进 `system.md`,`clamp()` 搬进 `rules.ink`;`scare`/`trust` 这类按同伴名字分支的函数留在游戏里(包不知道同伴叫什么)。宿舍游戏放一份包的副本(`packs/narrative-check/`,iCloud 的游玩副本和 CI 都不用另外取 inkwright),`check-ink --all --novelty --random 300` 两种语言的输出和换包前逐字相同。
- **"新建游戏"命令**:先选一个系统包(或者不用),再选模板,生成一套能玩的游戏,和现在的日志型模板一样。
- **检查**:`check-ink` 在系统包上单独跑一遍,每个包自带一个示例剧本给 CI 用。

## 6. 给别人用

- **格式稳定**:`schema: 2`。从这一版起改格式都要带迁移,并在 CHANGELOG 里写明。
- **报错**:配置错误、系统包对不上、实体 id 拼错,都用中英文说清楚是哪个文件哪一行。
- **教程**:第十章"做一个 RPG",每一刀一节,每节一个能玩的示例。
- **示例游戏**:每类至少一个公开的原创小游戏放在 ink-games(网页可玩),同时作为验收。
- **文档**:"选哪个系统包""写一个自己的系统包""ink 性能写法"。

## 7. 分刀

每一刀都要有一个真实的游戏能玩,并通过 `check-ink`。

| 刀 | 内容 | 验收 |
|---|---|---|
| R1 | 实体:固定和动态、种类、`spawn`/`stat`/`set_stat`/`alive`/`pick`、表格的行带属性、敌人区、网页、`check-ink` 和随机对局的统计;`party` 改成实体的简写 | 一个公开的原创小地城示例(教程 10.2,队伍 + 敌人 + 表里刷怪,没有一行战斗代码在引擎里)。原定的"4AD 改用实体"取消,见下 |
| R2 | 引擎侧计算和性能写法文档 | 4AD `--random 300` 的耗时降到现在的一半以下 |
| R3 | 规则系统包的格式、叠加、版本、"新建游戏"按系统选模板;第一个包:地城爬行(原创) | 用这个包从零做一个小地城,不写战斗代码。已做(2026-11-10):`packs/dungeon-crawl`,"新建游戏"命令,教程 10.3 |
| R4 | 背包数量、装备栏、状态效果 | 地城包用上:箭会用完、中毒每回合扣血。已做(2026-11-10):地城爬行 1.1,教程 10.4 |
| R5 | 成长和战役:经验、升级、天赋;角色卡笔记、`characters.from`、营地 | 一个英雄连续打两次冒险,升级和装备都带过去。已做(2026-11-10):教程 10.5 |
| R6 | 回合战斗包和示例;叙事检定包(宿舍游戏的规则整理出来) | 一场 3 对 3 的回合战斗;宿舍游戏改用这个包后行为不变。已做(2026-11-10):`packs/turn-battle`、`packs/narrative-check`,教程 10.6 |
| R7 | 公开:教程第十章、ink-games 上的包和示例、"安装系统包" | 一个没写过 Inkwright 的人照着教程做出一个能玩的小游戏(找人试) |

**4AD 不改用实体(2026-11-10 决定)。** 读了 4AD 的代码以后,原定的 R1 验收不成立:4AD 一场遭遇是"一群同样的怪"——一个数量,按"每满几点打死几只"成批地杀——不是一只只有自己生命的个体,拆成实体只会更重、不会更短;那 43 个 `foe_*` 大多是这场遭遇的开关(不死、厌恶某职业、免疫魔法……),战斗里反复读,改成外部函数读取会更慢,正好和 R2 反着来;`foe_hates` 是职业的 LIST 值,实体只存数字;掷骰的先后也会变,没法和旧结果按种子对比。所以 4AD 保持扁平变量,改作 R2 性能的基准;动态实体的真实验收挪到 R6 的 3 对 3 回合战斗(那里每个敌人确实各有各的生命和行动)。

顺序的理由:实体是一切的地基(R1)。地城最能暴露性能问题,而且有 4AD 当参照(R2、R3)。背包、状态、成长都挂在实体上(R4、R5)。回合战斗和叙事包是把前面的积木再组合一次(R6)。

## 8. 非目标

- 用户写的 JS 或其他脚本语言(安全、手机、网页、重放都过不去)。
- 网格上走位的战术战斗、实时战斗、多人。
- 可视化的规则编辑器(以后再说,先把格式定稳)。
- 把私有规则书的文字和表格放进公开仓库或系统包。
- 让 Inky 里能完整玩动态实体(只保证能编译、能走流程)。

## 9. 风险

| 风险 | 应对 |
|---|---|
| 动态实体存在字符串里,读写慢 | 解析结果按字符串缓存;热点交给引擎(R2);用 4AD 量 |
| 范围太大,做成框架 | 每一刀由一个真实游戏验收;原语只做"各类都要"的,特定玩法写进系统包 |
| 格式改来改去,别人的游戏坏掉 | `schema: 2` 加迁移;R3 之前不对外宣传系统包格式 |
| 系统包和游戏叠加后不知道值是从哪来的 | `check-ink` 和面板的检查器显示每个值的来源(系统还是游戏) |
| 穷举在动态实体上爆炸 | 穷举只认"活着几个、属性落在哪个区间";随机对局作为主要的平衡工具 |
| 4AD 改写时引入行为变化 | 机器人固定种子比对,先比对再删旧代码 |

## 10. 待定

1. 动态实体的 id 怎么起:自增数字,还是种类加序号(`goblin2`)。后者更好读,存档稍长。(R1 定了:`模板_编号`,如 `goblin_2`;编号前的 `_` 让同一类里不会撞,模板 id 在所有类之间不许重复。)
2. 敌人区放在正文和选项之间,还是状态栏里。手机上竖屏空间有限,可能需要一个折叠方式。(R1 定了:放在正文和选项之间,每类一行卡片,可以折叠,折叠状态跟着面板走;网页列在状态栏里。选项说的就是这些敌人,放在选项旁边最好对照。)
3. 角色卡笔记的 frontmatter 是否和 `characters` 的写法完全一致,好让作者手写角色卡。(定了:完全一致,id 默认取文件名;成长字段(经验、等级、天赋)是同一层的额外字段,R5 再加。作者只学一种写法,`characters.from` 读进来的和手写在 `game.md` 里的走同一个 `readConfig`。)
4. 系统包里的 ink,INCLUDE 路径怎么解析。现在 INCLUDE 相对于主剧本所在的文件夹,系统包放在别处时需要生成相对路径,或者支持 vault 绝对路径。(定了:生成相对路径,如 `INCLUDE ../../系统/地城/rules.ink`,写在 `_engine.ink` 里。现有的解析已经支持 `..`,剧本仍是标准 ink,Inky 和命令行一样能编译;不引入 vault 绝对路径这种只有插件懂的写法。游戏文件夹挪动后重新生成引擎即可,面板已经会提示引擎文件过期。)
5. "安装系统包"从哪里下载:GitHub 仓库的一个文件夹,还是打包成 zip。(定了:公开仓库 ink-games 里的 `systems/<id>/` 文件夹,`system.md` 列出它的文件,插件用 `requestUrl` 逐个取原始文件写进 vault。不用 zip:手机上没有解压,也不想为此加依赖;文件夹在 GitHub 上直接可读、可提 PR。)
6. 第一方的回合战斗规则用什么骰法(2d6 加属性,还是 d20)。(定了:2d6 加属性。和引擎默认的 `sum` 系统、宿舍游戏、五档结果一致,概率是钟形,小数值就有手感;d20 以后可以做成另一个包,不挡路。)
